# Tauri (Rust) Roadmap: From Zero to Secure Cross-Platform Desktop Apps

**72 sessions | 12 study weeks | approximately 228 hours | Tauri v2 | updated October 29, 2026**

This is a **standalone, practical roadmap** to build native desktop applications with **Tauri 2 and Rust**. You will start with basic Rust, build a TypeScript UI, learn to connect the UI to trusted Rust commands, store local data in SQLite, add native features, and ship an installable application. Each **Day** means one study session, not necessarily one calendar day. The main target is **Windows, Linux and macOS desktop**. Tauri also supports mobile targets, but Android/iOS are clearly marked as optional after the capstone.

**Final deliverable:** a **local-first desktop project organizer** with multiple projects, tasks, labels, search, SQLite, import/export, accessible keyboard workflows, secure file operations, background tasks, cross-platform packaging and automated tests. This is intentionally different from a browser-only app: the Rust side owns persistence and privileged OS operations, and the WebView owns presentation.

## Start here: prerequisites, platform and approach

You do **not** need to complete a separate Rust roadmap first: weeks 1–2 cover the minimum Rust concepts required, then deepen them throughout the project. Basic HTML and CSS familiarity helps; day 11 introduces frontend/TypeScript essentials. If you have never programmed, use *The Rust Programming Language* as your companion and take additional sessions wherever needed. Frontend choices: use **vanilla TypeScript + Vite** by default, or choose React, Vue or Svelte after the core Tauri concepts are clear. The backend remains Rust in all cases.

### What Tauri does (and does not do)

- **Tauri** wraps a web UI in a native application and exposes a constrained bridge to Rust/system features. It uses **WebView2 on Windows**, **WKWebView on macOS** and **WebKitGTK on Linux** rather than shipping the same full browser engine on every platform.
- Rust handlers run in the trusted application side; the frontend can only use explicitly exposed APIs. **Treat all arguments coming from the frontend as untrusted**, validate identifiers and file paths in Rust, and minimize plugin permissions.
- Shipping one source repository does **not** imply that one binary runs on every OS: prepare, test and package an artifact for each target, preferably on that OS or a corresponding CI runner.
- This is a **Tauri v2** guide. Avoid copying **Tauri v1** plugin imports, allowlist settings or configuration examples without checking the migration guide.

Verify the machine, then scaffold **one native app on the OS you are using**:

```bash

cargo --version
node --version
npm --version
npm create tauri-app@latest
# Choose: TypeScript / JavaScript → npm → Vanilla → TypeScript
```

Use the project name generated by the wizard in place of `YOUR_PROJECT_NAME`; available prompts/templates can change. **Do not use WSL as the default Windows GUI build path**: install and test the Windows toolchain natively. When trying a different UI framework, verify the framework's build output configuration and use the official Tauri integration docs. For the capstone, choose versions from current stable releases compatible with the selected Tauri release, and commit both Rust and npm lockfiles.

```bash
# In a scaffolded Tauri app root:
```

Your generated Tauri app may provide other scripts; consult `package.json`. `npm run tauri build` creates **OS-specific** output in the Tauri target/bundle directories. Never include credentials, signing keys, or personal task data in your Git repository.

## How one study session works

| Minutes | Block | What to do |
|---:|---|---|
| 10 | Recall | Retype a small example or explain a bug from the preceding session without notes. |
| 40 | Learn | Use the official page listed for the topic, then write notes in your own words. |
| 90 | Build | Type the exercise yourself; do not paste a completed solution. |
| 30 | Break and debug | Introduce a bad input, failing test or denied permission; trace the exact failure. |
| 10 | Save | Commit to Git and record *learned / confusing / next first step* in `journal.md`. |

Normal sessions are **3 hours**. Every 6th session is a **4-hour project and review** (60 × 3 hours + 12 × 4 hours = **228 hours**). Do not skip tests or security exercises to keep up with the calendar. A session is done only when the program runs, the **Done when** criterion has evidence, and the work is committed.

## Capstone acceptance criteria

Your **local-first desktop project organizer** is complete only when all of the following hold:

1. **Offline CRUD:** multiple projects and tasks with labels, due dates, filtering and search work without internet access.
2. **Persistence:** SQLite database survives restart; migrations preserve old data; backups and import/export have failure handling.
3. **Trust boundary:** Rust validates every privileged operation; the frontend does not receive broad filesystem access; unused capabilities are removed.
4. **Responsive UI:** keyboard navigation, announced form errors, light/dark themes and usable controls at narrow window sizes and 200% zoom.
5. **Reliability:** 30+ deterministic tests across Rust and frontend, a clean `cargo fmt --check`, a reviewed Clippy run and documented negative tests.
6. **Performance:** import at least 10,000 sample tasks without a frozen UI; cancellation leaves valid data; search performance is measured and recorded.
7. **Packaging:** installable bundle on the **host OS** and a tested install/uninstall or launch path; CI attempts Windows, Linux and macOS builds where runners are available.
8. **Communication:** README setup, screenshot/demo, test commands, architecture diagram, threat model, release notes and explicit supported-OS matrix.

Passing the capstone does **not** require paid certificates, a macOS signing identity, a Windows code-signing certificate, an always-on server or production auto-updates. Document which distribution prerequisites remain before publishing broadly. For genuine automatic updates, follow official guidance: signing and secure distribution are not optional shortcuts.

### Common mistakes to avoid

- Assuming any path chosen or typed by the UI is safe. **Validate on the Rust side**, including canonicalization and traversal checks where appropriate.
- Granting global filesystem or shell permissions to make one error disappear. Permission **and scope** are separate concerns for filesystem APIs.
- Running slow blocking operations directly on UI-sensitive threads, or spawning tasks without cancellation and lifetime management.
- Storing user data inside the installed app/resources folder instead of an application-specific writable data directory.
- Treating `tauri dev` as a release build, or testing a Windows bundle exclusively inside WSL.
- Copying obsolete Tauri v1 snippets into Tauri v2 without reviewing imports/config and capabilities.
- Assuming platform-native WebViews behave identically or every CI environment can produce every signed installer.
